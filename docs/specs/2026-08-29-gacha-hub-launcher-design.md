# Gacha Hub — дизайн лаунчера

Дата: 2026-08-29
Статус: согласовано, готово к написанию плана реализации

---

## 1. Что это и для кого

Десктопное приложение под Windows: один лаунчер для всех гача-игр пользователя,
независимо от того, через какой магазин они установлены.

**Аудитория — публичный релиз.** Приложение выкладывается так, что его скачивает
посторонний человек с чужой машиной, чужими дисками и чужим набором игр. Всё
проектируется исходя из этого, а не из конфигурации машины разработчика.

## 2. Проблема и ценность

Пять гача-игр живут в трёх разных магазинах. Чтобы запустить Wuthering Waves,
надо открыть Steam; чтобы Honkai: Star Rail — Epic Games; официальные лаунчеры
HoYoverse — третье место. Пользователь не хочет помнить, что где лежит.

**Ценность номер один: одна кнопка на игру, магазин скрыт.** Нажал PLAY на
Wuthering Waves — открылся Steam и запустил её. Нажал PLAY на Star Rail —
сработал Epic. Пользователю всё равно, что происходит под капотом.

**Ценность номер два: слева видно, что происходит прямо сейчас** по тем играм,
в которые он играет — промокоды, баннеры, видео разработчиков.

Фоновый арт — не ценность, а условие того, что приложение не стыдно держать
открытым. Он не должен требовать сложной инфраструктуры.

## 3. Границы

**Приложение делает:**

- находит установленные игры и позволяет добавить любую вручную, **без верхней
  границы на их количество**;
- запускает их через магазин или напрямую через .exe;
- показывает актуальные коды, баннеры и видео по играм пользователя;
- живёт в трее.

**Приложение НЕ делает:**

- не отслеживает, запущена ли игра сейчас, и не считает наигранное время
  (надёжно определить невозможно: запускается лаунчер игры, который сразу
  завершается, а в случае Steam процесса у нас нет вовсе);
- не проигрывает видео внутри себя — уводит в браузер;
- не раздаёт чужой арт со своих серверов;
- не собирает и не публикует утечки о будущем контенте.

## 4. Главный экран

Единственный основной экран. Одна игра в фокусе, остальные — в полке снизу.

```
┌──────────────┬────────────────────────────────────────┐
│              │                       НАЗВАНИЕ ИГРЫ     │
│   ПАНЕЛЬ     │                  запустится через Epic  │
│              │                                         │
│  промокоды   │            фоновый арт                  │
│  ──────────  │                                         │
│  баннеры     │                                         │
│  ──────────  │                          ┌───────────┐  │
│  видео       │                          │ ▶ Играть  │  │
│              │                          └───────────┘  │
│  ⚙ настройки │        [ полка с играми ]               │
└──────────────┴────────────────────────────────────────┘
```

**Размеры.** Окно по умолчанию 1150×760, минимум 940×600, размер и положение
запоминаются между запусками.

**Ширина панели: `clamp(300px, 24%, 400px)`.** На окне по умолчанию это ровно
300 px (26% ширины), на развёрнутом 1920 — 400 px (21%). Панель никогда не
раздувается на широком мониторе и не съёживается на узком. Растёт только арт.

**Название игры** — справа сверху, под ним подпись «запустится через Steam /
Epic Games / напрямую». Подпись существует специально: пользователь не помнит,
где что лежит, и лаунчер говорит это за него.

**Кнопка PLAY** — справа снизу, самый крупный элемент экрана.

**Полка с играми** — снизу по центру, выезжает при наведении курсора. Порядок
задаётся пользователем перетаскиванием в настройках. Текущая игра подсвечена.
Игр может быть сколько угодно: когда они перестают помещаться в ширину, полка
**прокручивается по горизонтали**, а не сжимает карточки до нечитаемых.

**Фоновый арт.** Для игры, про которую известен арт, — картинка. Для добавленной
вручную — **градиент, детерминированно выведенный из названия игры** (одно и то
же название всегда даёт один и тот же градиент, чтобы игра не меняла вид при
каждом запуске), с названием поверх. Пользователь может заменить его своим файлом
в любой момент. Пустого серого экрана не бывает никогда.

## 5. Панель

Сплошная колонка, прижата к левому краю, во всю высоту. Три секции сверху вниз,
разделённые линиями, и шестерёнка, прибитая к низу.

Панель показывает **только те игры, которые добавлены у пользователя**. Игра,
в которую он не играет, не попадает в панель вообще.

### 5.1. Промокоды (закреплены сверху)

Список активных кодов. Каждая карточка:

- сам код крупным моноширинным шрифтом;
- **под кодом** — таймер до сгорания («сгорит через 4 ч 12 мин», «осталось 4 дня»);
- справа — иконка игры, к которой относится код;
- правее иконки — кнопка копирования. Клик по всей карточке тоже копирует.

Код, сгорающий сегодня, подсвечивается. Истёкшие коды исчезают из панели, а не
превращаются в серый мусор.

Заголовок секции показывает количество активных кодов.

### 5.2. Баннеры

Показывают **настоящую картинку баннера**, а не текст. Каждая карточка:

- изображение баннера, поверх него внизу — название («Аид · 5★»);
- под изображением — полоса заполнения, показывающая, сколько прошло от всего
  срока баннера;
- под полосой — остаток времени цифрами.

Секция устроена каруселью: стрелки слева и справа, точки-индикаторы снизу.
В первой версии карусель листает **только идущие сейчас** баннеры. Листание
вперёд, к будущим, — следующая версия (это ограничение данных, а не интерфейса).

### 5.3. Видео и гайды

Карточки с **настоящими превью роликов**, а не с иконкой YouTube:

- превью во всю ширину панели;
- отметка длительности или слово «премьера» в углу;
- под превью — заголовок и строка «иконка игры + когда» («через 2 дня», «вчера»).

Клик открывает ролик в браузере пользователя. Видео внутри приложения не
проигрывается.

Ниже — зарезервированное место под гайды по актуальным персонажам. В первой
версии оно пустое.

### 5.4. Прокрутка

Промокоды и баннеры помещаются всегда. **Секция видео прокручивается внутри
себя**, шестерёнка остаётся прибитой к низу и никуда не уезжает.

Панель спроектирована так, чтобы **четвёртая секция добавилась без переделки
экрана** — под эндгейм-контент, который решено делать позже.

## 6. Список игр и обнаружение установок

### 6.1. Источник правды — сами магазины

Steam и Epic ведут машинно-читаемые списки установленного. Приложение их читает,
а не угадывает по именам папок.

**Steam:** файлы `steamapps/appmanifest_<appid>.acf` в каждой библиотеке. Дают
`appid`, `name`, `installdir`. Список библиотек берётся из
`steamapps/libraryfolders.vdf` (путь к самому Steam — из реестра — `HKLM\SOFTWARE\Valve\Steam\InstallPath` и `HKCU\Software\Valve\Steam\SteamPath`, плюс стандартные места).

**Epic:** файлы `*.item` в `C:\ProgramData\Epic\EpicGamesLauncher\Data\Manifests\`.
Дают `DisplayName`, `InstallLocation`, `LaunchExecutable`, а также
`CatalogNamespace`, `CatalogItemId`, `AppName` — три идентификатора, из которых
строится официальная ссылка запуска. **Записи с пустым `LaunchExecutable` — это
DLC, они отбрасываются.**

Это снимает три проблемы разом: не надо угадывать имена exe, не надо хранить
Steam appid в коде, и **не надо просить пользователя вводить Epic product id** —
он лежит в файле, который Epic пишет себе сам.

### 6.2. Установки мимо магазинов

Официальные лаунчеры (HoYoPlay и подобные) в манифестах не значатся. Для них
остаётся поиск по именам папок — но уже как запасной путь, а не основной:

- каталоги Epic и Steam на всех дисках;
- `Program Files` и `Program Files (x86)` на всех дисках;
- один уровень вложенности от корня каждого диска (`D:\Games\GenshinImpact`).

**Перечисление дисков — через `GetLogicalDrives` + `GetDriveType`, с пропуском
сетевых и оптических приводов.** Перебор букв A–Z с обращением к файловой
системе способен подвесить приложение на машине с отвалившимся сетевым диском.

Результаты дедуплицируются по пути. Сравнение расширений — без учёта регистра.

### 6.3. Первый запуск

Приложение показывает список найденного, разделённый на две группы:

1. **игры, про которые мы знаем** (есть контент — коды, баннеры, видео) —
   отмечены галочками по умолчанию;
2. **остальное установленное** — не отмечено, с честной подписью, что новостей
   и кодов по ним не будет.

Пользователь отмечает нужное и нажимает «Добавить отмеченные». Есть кнопка
«Пропустить» — тогда он добавляет игры сам.

### 6.4. Добавление вручную

Обязательная возможность, а не запасная. Пользователь указывает .exe, вписывает
название, при желании кидает свою картинку для фона. Такая игра запускается
наравне с остальными, но контента по ней нет.

**Количество игр ничем не ограничено.** Пять игр, про которые известен контент, —
это охват новостей, а не вместимость лаунчера. Добавить можно сколько угодно и
что угодно: десять гач, шутеры, эмулятор — лишь бы оно запускалось из Windows.
Ни в схеме конфига, ни в интерфейсе верхней границы нет и быть не должно.

### 6.5. Список игр = список подписок

Добавленная игра означает «я в неё играю» и попадает и в полку, и в панель.
Удалённая исчезает отовсюду. Отдельного экрана «какие новости показывать» нет.

Порядок в списке задаётся перетаскиванием и определяет порядок в нижней полке.

### 6.6. Несколько установок одной игры

Автоматика выбирает лучшую (магазин приоритетнее найденной по имени папки),
пользователь может поменять путь вручную. Отдельного интерфейса выбора нет —
случай редкий. При добавлении через скан найденные варианты показываются списком.

## 7. Запуск

Три способа, но для пользователя их два: «через магазин» и «свой .exe».

| Способ | Как | Откуда данные |
|---|---|---|
| Steam | `steam://rungameid/<appid>` | appid из `appmanifest_*.acf` |
| Epic | `com.epicgames.launcher://apps/<namespace>%3A<catalogItemId>%3A<appName>?action=launch&silent=true` | три id из `*.item` |
| Свой .exe | `CreateProcessW`, аргументы вектором, `current_dir` = папка exe | путь от пользователя |

**Аргументы запуска** разбираются по правилам Windows `CommandLineToArgvW`
(существующий `split_args` в `launch.rs` переиспользуется как есть). POSIX-разбор
недопустим: он съедает обратные слэши в путях. Незакрытая кавычка — видимая
ошибка, а не тихий запуск без аргументов.

`current_dir` = каталог exe: клиенты игр ищут свои данные относительно себя.

**Проверка «другая игра».** Существующая эвристика в `launch.rs` (сравнение имени
папки и имени exe с известными играми) в новой модели **становится
предупреждением с возможностью запустить всё равно, а не жёстким отказом.**
Причина: она даёт ложные срабатывания на легитимных конфигурациях — например,
когда все игры HoYoverse запускаются одним HoYoPlay.

## 8. Поведение

**Нажатие PLAY.** Кнопка на секунду показывает «Запускаю…», затем окно уходит
в трей. Если запуск не удался — окно остаётся, на месте кнопки появляется
причина и кнопка «Открыть настройки этой игры».

**Трей.** Крестик прячет окно, а не закрывает приложение. Возврат — клик по
иконке. Выход — через меню правого клика.

**Старт.** Открывается последняя успешно запущенная игра (`lastPlayed`
записывается в момент удачного запуска, а не при выборе в полке).

**Протухшие пути.** При старте каждый путь проверяется одним обращением к
файловой системе — это доли миллисекунды на игру, а не сканирование диска. Игра
с пропавшим файлом помечается значком в полке и в настройках, карточка
приглушается. PLAY по ней всё равно нажимается и выдаёт внятную ошибку с двумя
выходами: «Найти заново» (перечитать манифесты магазина — в большинстве случаев
чинит само) и «Указать вручную».

**Обновление данных.** Файл хаба тянется при старте, далее раз в 30 минут, пока
окно открыто, и дополнительно при возврате окна из трея. Таймеры на карточках
пересчитываются локально раз в минуту, чтобы «сгорит через 4 ч 12 мин»
уменьшалось на глазах.

**Нет интернета.** Показываются последние загруженные данные и тихая пометка об
их возрасте. Ни модальных окон, ни красных ошибок: запуск игр не зависит от сети.

**Автозапуск с Windows** — в первой версии отсутствует (см. §12).

## 9. Данные: файл хаба и сборщик

### 9.1. Архитектура

Выбран вариант «один сборщик, много читателей».

```
источники        сборщик на GitHub        приложения
──────────           ┌──────┐              ┌────┐
HoYoverse ──┐        │      │   один       │ ПК │
Kuro ───────┼──────► │ раз  │ ──файл────►  ├────┤
Hypergryph ─┤        │ в час│              │ ПК │
YouTube RSS ┘        └──────┘              └────┘
коды (руками) ─────────┘
```

**Приложение не умеет читать сайты.** Оно скачивает один готовый файл. Умение
разбирать каждый источник живёт в скрипте на GitHub.

Причина выбора: когда источник меняет формат — а он меняет — починка это один
коммит в скрипт, а не сборка новой версии приложения и ожидание, пока все
обновятся. Кроме того, промокоды не публикует машинно-читаемо никто, поэтому
человеческий канал сбора нужен в любом случае; раз он есть, остальное едет
в тот же файл бесплатно.

### 9.2. Что в файле

- **каталог известных игр** — соответствие «установленная игра → наш
  идентификатор контента», по Steam appid, по идентификаторам Epic и по
  шаблонам имён папок. Каталог лежит в том же файле, а не в коде: **добавление
  поддержки шестой игры не требует обновления приложения**;
- **промокоды** — код, игра, награда, момент истечения;
- **баннеры** — игра, название, ссылка на картинку, начало и конец;
- **видео** — игра, заголовок, ссылка на YouTube, ссылка на превью, время
  публикации или премьеры.

### 9.3. Источники для сборщика

- **видео** — официальные RSS-ленты каналов YouTube (открытый механизм самого
  YouTube, ключи не нужны). Уже вышедшие ролики подтягиваются надёжно; анонсы
  ещё не начавшихся премьер — не всегда, их дозаносят руками;
- **превью роликов** — адрес выводится из идентификатора видео по постоянному
  шаблону YouTube;
- **баннеры и новости** — официальные страницы и ленты игр;
- **промокоды** — ручной канал.

### 9.4. Цепочка источников в приложении

Уже реализована в `hub.rs` и переиспользуется:

1. удалённый файл по `hubUrl` (только `https`, таймаут 5 с), результат кешируется;
2. локальная подмена `%APPDATA%\<id>\hub.json` — для правки данных без пересборки;
3. последний удачный кеш;
4. файл из комплекта поставки.

Источник, из которого пришли данные, виден в интерфейсе.

**Загрузка хаба не блокирует первый экран.** Сейчас интерфейс ждёт все запросы
разом, и медленный `hubUrl` задерживает появление окна на 5 секунд. Хаб должен
грузиться отдельно и дорисовывать панель по готовности.

### 9.5. Картинки

Арт баннеров и превью роликов приезжают в файле ссылками. **Скачивает и кеширует
их Rust**, интерфейсу отдаётся локальный файл. Так строгая политика безопасности
страницы остаётся нетронутой, а картинки не пропадают без сети.

## 10. Безопасность

Файл хаба — данные из сети, поэтому проектируем так, будто он враждебный.
Принцип: **файл может только рассказывать, но не может ничего делать.**

1. **Никаких путей и команд в схеме.** В файле бывают только текст и ссылки.
   Самое злое, что может сделать подменённый файл, — показать неверный текст.
2. **Ссылки только `https://`.** Всё остальное отклоняется (уже реализовано
   в `openSafeUrl`). Это закрывает `file://` и произвольные обработчики протоколов.
3. **Текст рисуется как текст**, никогда не как разметка.
4. **Ограничение на размер ответа**, и запрет перехода с `https` на `http` при
   редиректах.
5. **Кривой файл = как будто его нет**: берётся прошлая хорошая копия.
   Пользователь видит вчерашние данные, а не мусор и не пустой экран.

Файл лежит в том же репозитории, откуда люди скачивают само приложение, поэтому
новой стороны, которой надо доверять, не появляется.

Политика безопасности страницы (CSP) уже ужесточена; правило `ws:` нужно только
для разработки и в релизной сборке не требуется.

## 11. Модель данных

### 11.1. Главное изменение

Сейчас игра — это константа в коде: массив `GAMES` в `catalog.rs`, а
`launch_game` отказывается работать с идентификатором, которого там нет. Игра,
добавленная пользователем, не может быть запущена в принципе.

**Игра становится записью в конфиге.** Каталог превращается в необязательное
обогащение: «про эту игру мы знаем контент».

### 11.2. Схема конфига (версия 2)

```json
{
  "version": 2,
  "hubUrl": null,
  "lastPlayed": "hsr",
  "games": [
    {
      "id": "hsr",
      "title": "Honkai: Star Rail",
      "contentId": "hsr",
      "launch": {
        "kind": "epic",
        "namespace": "a2dcbb9e34204bda9da8415f97b3f4ea",
        "catalogItemId": "101391ece6024e069a7cb8cf22104399",
        "appName": "86ae9acccf8443e18fca6950e0181288"
      },
      "installPath": "C:\\Program Files\\Epic Games\\HonkaiStarRail",
      "exePath": "C:\\Program Files\\Epic Games\\HonkaiStarRail\\launcher_epic.exe",
      "args": "",
      "background": null
    }
  ]
}
```

**`games` — массив, а не словарь.** Порядок значим: он задаёт полку. Словарь дал
бы случайный порядок при каждом запуске.

**`contentId`** связывает игру с контентом в файле хаба. `null` — игра
добавлена вручную, контента по ней нет.

**`launch.kind`** — `steam` (нужен `appid`), `epic` (нужны три идентификатора)
или `exe` (нужен `exePath`).

**`installPath`** используется для проверки, что игра не переехала.

**`background`** — путь к картинке, которую подставил пользователь.

Размер и положение окна хранит `tauri-plugin-window-state` в собственном файле,
в конфиге приложения их нет.

### 11.3. Миграция

Конфиг версии 1 (текущий формат со словарём `games` и полями `launchMode` /
`epicProductId`) читается и переносится в версию 2 автоматически: ключи словаря
становятся `id` и `contentId`, `launchMode` раскладывается в `launch.kind`.
Порядок игр при миграции берётся из порядка каталога.

Существующая устойчивость чтения сохраняется: битая запись по одной игре
отбрасывается с записью в лог, остальной конфиг живёт; в `.broken`
переименовывается только синтаксически сломанный файл.

Существующая атомарная запись (временный файл + переименование) сохраняется.

## 12. Состав первой версии

**Входит:**

- игра как данные, а не как константа; миграция конфига;
- чтение манифестов Steam и Epic, поиск по папкам как запасной путь;
- экран первого запуска со списком найденного;
- добавление вручную, удаление, перетаскивание порядка;
- запуск: магазин и свой .exe; проверка протухших путей и «Найти заново»;
- главный экран целиком: арт, название, PLAY, выдвижная полка;
- панель: промокоды, баннеры, видео — по играм пользователя;
- фон для игры без арта: генерируемая заливка плюс своя картинка;
- цепочка источников данных, кеш картинок в Rust;
- трей: крестик прячет, PLAY прячет, клик возвращает;
- сборщик на GitHub в минимальном виде: видео через RSS, коды руками.

**Не входит, с причинами:**

| Что | Почему отложено |
|---|---|
| Автообновление приложения | Требует ключей подписи и настроенных релизов. Данные при этом обновляются сами — ради этого и выбран сборщик. |
| Листание баннеров вперёд | Ограничение сбора данных, а не интерфейса. |
| Запуск игры из меню в трее | Удобство поверх работающего лаунчера. |
| Автозапуск с Windows | Требует объяснения в интерфейсе; работы на пять минут, но не сейчас. |
| Гайды по персонажам | Место на экране зарезервировано, источника данных нет даже в замысле. |
| Эндгейм-контент | Решено, что будет. Не проектировался. Панель заложена растягиваемой, четвёртая секция добавится без переделки экрана. Главный вопрос при проектировании — откуда брать сроки циклов по пяти играм. |
| Английский язык | Приложение русскоязычное. |
| Отслеживание запущенной игры и время в игре | Надёжно не реализуется, см. §3. |

## 13. Этапы

После каждого этапа приложением можно пользоваться.

**Этап 1 — «Запускать».** Новая модель игры, чтение манифестов, запуск, главный
экран с артом, названием, PLAY и полкой. Панель показывает данные из комплекта.
На этом месте исходная задача — не открывать три лаунчера — уже решена.

**Этап 2 — «Видеть».** Три секции панели, картинки, таймеры, цепочка источников,
кеш изображений. Параллельно и независимо — сборщик в отдельном репозитории.

**Этап 3 — «Настраивать».** Экран первого запуска, настройки, добавление игр
вручную, перетаскивание порядка, трей, пометки протухших путей.

Объём слишком велик для одного плана реализации. **План пишется на этап 1**,
этапы 2 и 3 получают свои планы, когда предыдущий закрыт. Сборщик — отдельный
проект в отдельном репозитории, со своим планом, и делается независимо.

## 14. Что происходит с существующим кодом

**Переиспользуется:** атомарная запись и устойчивое чтение конфига; цепочка
источников хаба; `split_args` с правилами Windows; каркас Tauri, capabilities,
CSP.

**Переписывается:** `catalog.rs` (превращается в таблицу соответствий из файла
хаба); `detect.rs` (чтение манифестов вместо угадывания по папкам); `commands.rs`
(новый набор команд); весь фронтенд.

**Чинится по ходу** (найдено в ревью, переживает переделку):

- перечисление дисков через `GetLogicalDrives` вместо перебора A–Z;
- кеш обнаружения не держит мьютекс во время обхода дисков — иначе сканирование
  блокирует остальные команды;
- загрузка хаба уезжает с критического пути первого экрана;
- машинно-зависимый тест `detect_all_finds_local_games` заменяется на тесты
  разбора манифестов и сопоставления, которые проходят на любой машине;
- ограничение размера ответа и запрет понижения `https` → `http`.

## 15. Открытые вопросы

Не блокируют начало работы, но требуют решения по ходу.

1. **Адрес удалённого файла хаба.** Репозиторий сборщика ещё не создан.
   До его появления приложение работает на файле из комплекта и локальной
   подмене.
2. **Охват каталога контента.** Пять стартовых игр плюс правила сопоставления
   надо выписать явно и проверить на реальных установках. Это влияет только на
   то, по каким играм показывается контент, и **никак не ограничивает, сколько
   игр пользователь добавит**.
3. **Часовые пояса.** Сроки кодов и баннеров привязаны к серверам игр
   (Asia / Europe / America), а показываются в местном времени пользователя.
   Формат хранения времени в файле хаба должен быть однозначным (момент времени
   с зоной, а не дата строкой), иначе «сгорает завтра» будет врать людям в
   других поясах.
4. **Проект не под контролем версий.** `git init` не выполнялся. Перед началом
   работы стоит завести репозиторий, иначе откатывать переделку будет нечем.
